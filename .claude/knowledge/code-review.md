# Code Review — Accumulated Knowledge

> Living notes for `/code-review` + `code-reviewer`: recurring smells and judgment calls learned with use.
> Authority for the anti-pattern codes stays in `.claude/patterns/code-review-checklist.md`.

## Recurring findings

- **Cache-aside + soft-delete interaction:** when a repository's `findById` does not filter `deleted_at: null` at the Prisma level (user repo does `findUnique` without the deleted-at filter), a soft-deleted entity can be cached and returned as live on subsequent hits. Always verify whether the underlying Prisma query includes the soft-delete filter; if not, add a post-deserialize guard or fix the Prisma query.
- **Write-then-evict ordering:** every `inner.write → await invalidateCache` pair has a sub-TTL stale window for concurrent readers. This is inherent to write-aside invalidation; document the worst-case window (= TTL) in env comments, especially for security-adjacent paths (webhook URLs, token data).
- **`container.resolve()` per-request in middleware:** resolving singletons from the DI container on every request is a performance and consistency smell. Capture singletons in the factory-function closure at middleware creation time.
- **`InMemoryCacheProvider.increment` ignores TTL:** the in-memory mock stores counters indefinitely, diverging from real Redis which applies a TTL on first insertion. Security-gate tests that rely on TTL expiry will produce false-passing results.

## Judgment calls / calibration

- The confused-deputy risk of unscoped-cache + in-memory `accountId` guard (`CachedDevicesRepository.findById`) is sound when Redis is a trusted internal boundary and not shared across tenants or apps. The trust assumption must be named at the method level as an auditable invariant.
- Full-parity codec (including `password` bcrypt hash and `refreshTokenHash`) in `cached-user-repository.ts` is intentional and correct: nulling credentials on a cache hit would create hit≠miss divergence. The rationale should be documented at the codec (already is, as of this review).
- `signUpTransaction` not evicting is correct because the new user id cannot be in the cache. However, if that method is ever changed to update an existing user, the no-evict assumption silently breaks — add a comment.

- **Dead-type select in sandbox forms:** when a SelectField exposes message-type options but the send handler ignores the selected value and always calls the text endpoint, the select is visually meaningful but functionally dead. Either remove it (until a second type exists) or gate `handleSend` on `formData.messageType` routing. The pattern recurs any time spec §x says "text only, type selector is for future use."
- **Stale-closure in device-select useEffect — validated fix pattern [Med, 2026-09-16]:** `useFormState.setField` depends on `formData` and recreates on every form change, so any `useEffect` deps array that includes `setField` (required by exhaustive-deps once the effect calls it) re-invokes on every keystroke across the WHOLE form, not just the field the effect cares about. Confirmed safe in `useSandboxComposer.ts` (`web-rebuild-fase-8-sandbox`): depend on primitives derived from formData (`firstConnectedId`, a `selectedIsConnected` boolean) + `setField`, and guard the body with the same condition that would make it a no-op — the extra re-invocations are harmless no-ops, the effect converges in one extra render, and no eslint-disable is needed. This is the correct trade-off for a feature diff; the real fix (make `setField`'s identity stable) requires `useFormState` to stop closing over `formData` (e.g. read it via a ref internally), which is shared-hook surgery out of scope for a single-module refactor — don't drive-by it into an unrelated diff.
- **`updateStatus` unscoped-by-account in DisconnectDeviceUseCase:** this is intentional and documented in `IDevicesRepository` — the ownership check happens at `findById(accountId, id)` before `updateStatus(device.id, ...)` is called. The pattern is safe as long as `device.id` comes from a prior scoped read. Never forward `device.accountId` from an unscoped method into a scoped query (confused-deputy, per the interface comment).

- **Shadow token rename drift:** when semantic-tokens.ts renames shadow tokens (e.g. `card-hover` → `shadow.cardHover`), grep ALL component files for the old token string before closing the task. Chakra silently ignores unknown `boxShadow` values — no build error, no TS error, only a visual regression. The check `grep -rn '"card-hover"' apps/web/src --include="*.tsx"` must pass clean after any shadow rename.
- **Polling query: write-before-send contract verification:** when a FE polling hook fires `GET /resource/:id` after a `POST` that returns the id, confirm the backend `POST` handler writes the row to the DB BEFORE it attempts the side-effect (gateway call) — otherwise the first poll arrives before the row exists and gets a 404. In `SendTextMessageUseCase`, `outboxRepository.create()` is called at line 95 and `gateway.sendText()` at line 121; the 202 response carries the committed id, so `GET /messages/:id` is guaranteed to find the row. Document this ordering as an invariant when reviewing messaging use cases.
- **MobileBottomNav item duplication:** `MobileBottomNav.tsx` maintains its own flat array of nav items in parallel to `navigation.ts` (which is the authority for the sidebar). Adding a nav item requires editing both files. Prefer extending `NavigationItem` with an optional `matchPaths?: string[]` field so both surfaces draw from the single `navigationSections` source. Flag any PR that adds items to one and not the other.
- **`useColorMode` in SidebarNav is not F-H16:** using `colorMode === "dark"` to toggle icons (FiSun/FiMoon) or translate strings ("Switch to dark/light theme") is a legitimate, non-semantic-token use of `useColorMode`. F-H16 only applies to color value selection — `isDark ? "red.600" : "blue.600"` — not to icon or text selection. Do not flag the SidebarNav color-mode toggle as F-H16.

- **Concrete-class injection without @inject in tsyringe:** when a constructor parameter type is a concrete `@injectable()` class (not an interface), tsyringe resolves it via `reflect-metadata` type token without requiring `@inject(TOKEN)`. This works today because `emitDecoratorMetadata: true` emits the class constructor as the design:paramtypes entry. It breaks if: (a) the param type is imported as `type` only (erased at runtime), (b) a second impl of the same interface replaces the class, or (c) the class is moved to a different module and the singleton registration is missed. The canonical pattern for this project is to always use `@inject(DI_TOKENS.X)` for every parameter — even for concrete class tokens — so the wiring is explicit and survives refactors.

- **waitForToken spin-safety in drain loop:** the drain's `waitForToken` private method avoids busy-spin by sleeping `Math.max(msUntilNextToken(), 1)` ms between retries. The `unref()` on the internal `setTimeout` prevents the timer from blocking graceful shutdown. Exit is conditional on `isConnected` re-checked inside the loop, so a device that disconnects while waiting returns `false` promptly (no indefinite hold on the single-flight guard). The pattern is sound; the only risk is the drain holding the guard indefinitely if the device reconnects faster than the token refill — but that maps to a legitimate live-drain, not a starved session.

- **Token bucket `msUntilNextToken` called inside `waitForToken` after `tryConsume` returned false:** calling `msUntilNextToken` right after `tryConsume` returned false means the refill math re-runs (`bucketFor`) but the elapsed time since the last consume is near zero. The computed sleep is therefore accurate (it is `ceil((1 - tokens) / refillPerMs)` where `tokens` is already negative of one token). No double-consume risk because `msUntilNextToken` is a read-only path; only `tryConsume` mutates `bucket.tokens`.

- **Route-count claims in planning docs need a grep, not a read-through:** a roadmap/spec that states "N rotas reais" as a factual, AC-verifiable claim (e.g. `web-rebuild-roadmap-5b5abe`) should be checked by literally grepping every `*.routes.ts` file for `router.METHOD(` calls, not by trusting a narrative count — off-by-a-few is easy when auth alone has 13 routes across sign-up/in/google/reset/refresh/email-verification/me/profile/avatar/sign-out/delete. In this review the doc's own Apêndice B enumeration (37 business + 2 health = 39) didn't match its own "34 rotas" header — the miscount was internally self-detectable by just adding up the doc's own bullet groups.
- **Phase-dependency diagrams drift from the dependency table:** an ASCII sequencing diagram (§6-style) is handwritten and easy to get subtly wrong even when the per-phase "Depende de" table (§4-style) is correct — check that every arrow in the diagram has a matching table row and vice versa. The common failure mode is a phase's true dependency (e.g. a shared-types package needed by a later phase) missing from the diagram while an unrelated phase gets merged into the wrong funnel.

- **Chakra v3 `{colors.X}` / `{shadows.X}` references inside raw CSS strings (e.g. `backgroundImage="linear-gradient({colors.status.success.bg}, ...)"`) are a real, generic engine feature** — `expandTokenReferences` (`@chakra-ui/react/dist/esm/styled-system/expand-reference.js`, called from `token-dictionary.js`'s `expandReferenceInValue`) resolves any `{category.path}` token reference to its CSS var, in ANY prop value, not just a whitelist. It correctly flips with `_dark` because the var is defined twice (root selector + the dark-condition selector) and CSS custom properties cascade through Portals (a Portal is still a DOM descendant of `<html>`, where `next-themes` sets `class="dark"`). Do not flag this pattern as a hack; verify only that the referenced token actually exists (that's what `tokenContract.spec.ts`'s `TOKEN_REF` regex is for) — [2026-09-16] [Med].
- **A source-only workspace package (`package.json` `main`/`types`/`exports` → `./src/index.ts` directly, no build step) is NOT swept into Vite's dep pre-bundle** — confirmed empirically (`.vite/deps/_metadata.json` after a forced re-optimize) in `@pombo/theme`. This is a cleaner fix than `apps/web/aliases.ts`'s per-app alias workaround (used for `@pombo/shared-types`, whose `main` points to a *built* `dist/index.js`, which DOES get pre-bundled and goes stale without the alias). When a new workspace package is added as source-only, point its own `package.json` at `src/index.ts` instead of adding an app-level alias — [2026-09-16] [Med].
- **A "scan `src` for token-literal strings" contract test must include every package that hand-authors token names, not just the top-level app** — `apps/web/src/app/theme/tokenContract.spec.ts`'s `SRC_ROOT` resolves to `apps/web/src` only, so it never scans `packages/theme/src/foundations/recipes.ts` (or any sibling foundations file), which is exactly where semantic-token-name strings are written by hand and exactly where the next design-handoff pass will edit most. Extend `collectSourceFiles` (or add a parallel scan) to cover every package that references its own tokens by string — [2026-09-16] [Med]. **Resolved in the same task:** the spec now also scans `THEME_ROOT` (`packages/theme/src`) and asserts it found theme files — do not re-report it as open.
- **CORS `exposedHeaders` is a silent, environment-dependent break for any FE code that reads a non-simple response header** (`Retry-After`, custom rate-limit headers, etc.): same-origin dev (Vite proxy) never exercises the browser's CORS header-visibility restriction, so `error.response.headers["retry-after"]` reads fine locally and returns `undefined` only in a real cross-origin production deploy — no type error, no lint warning, no test failure (mocked axios responses don't enforce browser header visibility either). `web-rebuild-fase-6-auth` found and fixed exactly this for `Retry-After` (`apps/api/src/core/http/app.ts`'s `cors({ exposedHeaders: [...] })`). When reviewing any diff that adds a `response.headers["x-..."]` read on the frontend, grep the API's `cors()` config for a matching `exposedHeaders` entry — [2026-09-16] [Med] (proposed code: `X-H-cors-exposed-header-fe-read`).
- **Single-snapshot rollback clobbers concurrent optimistic mutations on the same list:** `frontend.md`'s canonical optimistic-delete shape (`onMutate` snapshots the whole list once, `onError` restores that whole snapshot) is correct for one in-flight mutation but not for two overlapping ones sharing the same list query — a `ConfirmDialog` built on `useConfirm()` closes the instant `confirm()` fires (before the mutation resolves), so a user can start a second delete while the first is still in flight. If the first mutation then fails, its `onError` restores the pre-both-deletes snapshot, resurrecting the second (possibly already-succeeded) device in the list until `onSettled`'s `invalidateQueries` refetch corrects it. Bounded (self-heals in one round-trip, no server-side data loss) but a real, reachable UI glitch — first observed in `useDeleteDevice` (`web-rebuild-fase-7-devices`). Fix: on error, merge the single failed item back into the *current* cache (read fresh, append only if the id isn't already present) instead of overwriting with the original full snapshot. Any module copying the canonical snippet inherits the same gap — worth hardening the doc's example, not just the call site. [2026-09-16] [High].
- **A raw-palette-to-semantic-token swap is not always a no-op — check the shade, not just the color family.** `bg.brand.solid` resolves to `{colors.brand.600}` in light mode (not `.500`), so swapping a raw `bg="brand.500"` for the semantic token would visibly darken the element in a "keep the look" phase. `ProfileAvatarCard.tsx:96` (and the pre-existing `SidebarUserMenu.tsx`/`MobileHeader.tsx`) keep the raw token for exactly this reason — legitimate, but it must be a *documented* exception (Decisions log / "Pendências herdadas"), not a silent AC miss: `web-rebuild-fase-9-profile-api`'s AC-6 ("nenhuma cor crua da paleta no card de avatar") went unmet with no note explaining why. When an AC asks to remove a raw palette token, verify whether an exact-shade semantic equivalent exists before flagging the swap as a trivial fix — if it doesn't, the right output is a documented deferral, not a silent carry-over. [2026-09-16] [Med].
- **Resolved in the same task:** all three avatars (`ProfileAvatarCard`, `SidebarUserMenu`, `MobileHeader`) now use `bg="bg.brand.solid"` + `color="text.onBrand"` (the primary-button pairing), deliberately accepting the light-mode shade change from `brand.500` to `brand.600` — documented in the spec's Decisions log with the measured contrast (white on `brand.500` was ~2.5:1). Residual gap, not re-open: the new light-mode ratio (white on `brand.600` ≈ 3.77:1) still falls short of WCAG AA 4.5:1 for normal text — `SidebarUserMenu`/`MobileHeader` render the fallback initials at `fontSize="xs"` (12px), well under the "large text" 3:1 exemption threshold (≥18.66px bold), so full AA compliance there needs a further token change (not just this swap). Dark mode (`#052e21` on `brand.500` ≈ 5.83:1) is comfortably AA. Tracked generically by the Fase 10 roadmap item "contraste AA nos pares `text.*` × `bg.*` (verificado na galeria)" — [2026-09-16] [Med].
