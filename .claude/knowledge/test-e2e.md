# E2E Testing — Accumulated Knowledge

> Living notes for the `/test-e2e` skill + `e2e-test-writer`: flaky-test root causes, locator tricks, POM lessons.
> Fills **with use**. Authority for the conventions stays in `.claude/patterns/e2e.md`.

## Selector Strategies
- **Duplicate `<nav aria-label>` landmarks (sidebar vs. mobile bottom nav).** `SidebarNavItems` and `MobileBottomNav` both render `<nav aria-label="Navegação principal">` and are never unmounted — only hidden by a CSS breakpoint (`display: none`). `page.getByRole("navigation", { name }).filter({ visible: true })` resolves to whichever one the current viewport actually shows, without `nth()`/`first()`. Bonus: the *same* POM locator then drives both the desktop-sidebar spec and the `test.use({ viewport })`-scoped mobile-bottom-nav spec — no separate locator needed per breakpoint.
- **`AppModal` instances persist across conditional JSX branches at the same tree position.** `CreateDeviceModal` renders a name-form `<AppModal>` then, after create, an early-return secret-reveal `<AppModal>` — same component type at the same position, so React updates in place rather than unmount/remount. One `getByTestId("app-modal")` on the POM tracks the modal correctly across that step without re-querying or waiting for a fresh mount.
- **`getByLabel` also matches a bare `aria-label`** (no wrapping `<label>` needed) — `ApiTokenRevealModal`'s read-only `FormField` sets `aria-label={t("apiToken.reveal.label")}` directly (no `label` prop), and `getByLabel(/token de api|api token/i)` still resolves it; `aria-label` is part of the accessible-name computation Playwright's locator uses.
- **`AppModal` primary button vs. header close trigger can share the exact same accessible name.** When `primaryActionLabel` is the generic "Fechar"/"Close" word (a reveal-only modal with no real "cancel" semantics), it collides with the header `DialogCloseTrigger`'s `aria-label={t("actions.close")}` — same text, same dialog. `getByRole("button", { name: /fechar|close/i })` is ambiguous here; use the pre-approved `app-modal-primary` testid instead (it's a shared, already-sanctioned id, not a new one).
- A `NativeSelectField`'s hidden placeholder option (`<option value="" disabled hidden>{placeholder}</option>`, used for a query's loading/error/offline-state copy — see `GroupRecipientField`) is still readable via `expect(selectLocator).toContainText(...)`: the HTML `hidden` attribute only affects rendering, not `textContent`.

## Flaky Test Fixes
- **A card driven by `useQuery` with an "empty vs. exists" CTA branch shows a brief loading skeleton with NEITHER cta on screen** (`ApiTokenTab`'s generate/regenerate button). A POM method that branches on "which CTA is visible" must `await expect(ctaA.or(ctaB)).toBeVisible()` before checking `isVisible()` — checking immediately after `goto()` races the fetch and always falls into the "empty" branch.
- **`useUnsavedChangesGuard` (`shared/hooks/useUnsavedChangesGuard.ts`) blocks the browser back button via a "duplicate history entry" trick**, not a real navigation cancel: when `isDirty` flips true it pushes a spare history entry pointing at the *same* URL; a canceled `window.confirm` on `popstate` re-pushes that duplicate again. One `goBack()` with the dialog dismissed (`page.once("dialog", d => d.dismiss())`) reliably proves the block (`toHaveURL` never changes). Proving the "user confirms and actually leaves" path needs a SECOND `goBack()` (the first only consumes the safety duplicate) — flaky enough headless that `settings/profile.spec.ts` only asserts the deterministic cancel path.

## Page Object Patterns
- `cardByName(name).first()` after `.filter({ hasText: name })` is the documented convention (`patterns/e2e.md`'s own afterEach skeleton), not an `E-H2` violation — the filter already disambiguates; `.first()` just collapses a should-be-unique match to a strict-mode-safe single Locator. Only flag `.first()`/`.last()`/`.nth()` when it's substituting for a missing filter, not following one.
- `next-themes`' `setTheme()` (the app's color-mode toggle) writes to `localStorage` synchronously inside the click handler — read it right after `.click()` resolves, no poll/wait required.
- **File upload through a custom-styled trigger** (a button that calls `fileInputRef.current.click()` on a hidden, unlabeled `<input type="file">` — see `ProfileAvatarCard`) has no accessible name to `getByLabel`/`getByTestId` on the input itself. Intercept the real `filechooser` event off the *visible* trigger instead: `Promise.all([page.waitForEvent("filechooser"), triggerButton.click()])` then `chooser.setFiles(...)`.
- **`WHATSAPP_ENABLED=false` makes a device permanently unable to reach `CONNECTED`** in the e2e stack — any UI gated on a connected device (Sandbox composer/queue, group pickers) is unreachable through the real backend. `page.route` mocking `GET /devices` + the relevant send/status/groups endpoints is the sanctioned exception documented in `patterns/e2e.md` § Database CRUD; `messaging/sandbox-send.spec.ts` is the reference implementation (module-level mock helpers, not per-test duplication).

## Dead Ends
- `patterns/e2e.md`'s cited debounce source-of-truth file `useDebouncedValue.ts` does not exist in this codebase; the real hook is `shared/hooks/useDebounce.ts` and individual call sites pass their own delay (devices list search is 300ms, not 500ms). The documented 500ms `waitForTimeout` convention still works as a safe upper-bound wait (500 > any ≤500ms debounce in the app today) — keep using 500, but don't assume it's the literal debounce value when writing a comment that cites the source.
